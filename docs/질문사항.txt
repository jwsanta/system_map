대상 독자: 이 설계를 검토하고 구축할 AXA 인프라 운영팀·보안팀·네트워크팀

설계서를 [docs/IT_Infra_Impact_Map_Design.md](docs/IT_Infra_Impact_Map_Design.md)에 작성했습니다. 커밋은 하지 않았습니다.

**질문하신 항목에 대한 결론**

1. **도구:** Ansible(SSH/WinRM)로 수집하고, PostgreSQL에 저장하고, Python으로 연결 매칭과 영향도를 분석합니다. 화면은 FastAPI + React + Cytoscape.js로 만듭니다. Neo4j는 DB를 두 종류 운영해야 하는 부담이 있어 1차에서는 쓰지 않고 PostgreSQL 재귀 쿼리로 처리합니다.
2. **Agentless 여부:** 기본은 Agentless이며 대상 서버에 패키지를 설치하지 않습니다. 쓰는 것은 `ss`, `/proc`, `rpm`, `dnf`, platform-python, PowerShell 5.1처럼 OS에 기본으로 있는 것뿐입니다.
   - 다만 3시간마다 한 번 찍는 스냅샷으로는 배치, 야간 작업, Cloud 연동처럼 특정 시간대에만 생기는 통신을 거의 놓칩니다.
   - 그래서 **5분마다 실행되는 샘플러 스크립트**(systemd timer / 예약 작업)를 함께 둘 것을 권장합니다. 상주 프로세스는 없습니다. 이 데이터로 요일×시간 히트맵을 만들고, "몇 시부터 몇 시까지 down 가능한가"의 근거로 씁니다.
   - 정밀 추적(eBPF, Sysmon)과 성능 지표(exporter)는 선택 사항인 Agent 방식으로 분리했습니다.
3. **패치 영향 판단:** `ldd` 같은 정적 분석 대신, 프로세스가 **실제로 메모리에 로드한 library**(`/proc/<pid>/maps`, `Process.Modules`)를 패키지와 매칭합니다.
   - 실제로 문제가 생기는 시점은 패치 직후가 아니라 **서비스를 재시작할 때**입니다. 그래서 결과물은 "재시작이 필요한 프로세스", "soname이 바뀌는(ABI) 위험", 그리고 "그 프로세스가 다운될 때 영향받는 주변 시스템(Blast Radius)"을 중심으로 구성했습니다.
   - Windows는 누적 업데이트가 사실상 항상 재부팅을 요구하므로, 재부팅 영향과 재부팅 가능 시간대를 중심으로 다룬다고 명시했습니다.
4. **HTML로 할지:** 운영은 **웹 애플리케이션**을 권장합니다. 검색, 클릭해서 내려가 보기, 패치 시뮬레이션, 이력 비교가 필요하기 때문입니다. **정적 HTML은 PoC 단계와 CAB 제출용 내보내기**로 쓰면 됩니다. 두 방식이 같은 JSON을 쓰도록 설계해서 PoC 결과를 그대로 웹 화면으로 발전시킬 수 있습니다.

**추가로 제안한 결과물:** 패치 후 검증 리포트, 재시작 누락 현황, 미승인 통신 탐지, 변경 이력, SPOF 리포트, EOS 현황입니다. Windows Server 2016은 2027년 1월에 연장 지원이 종료됩니다.

**검토 시 미리 결정이 필요한 사항**(부록 A에 정리):
- 수집 계정 권한 범위(Linux sudo, Windows 로컬 관리자 또는 JEA): 보안팀 승인 필요
- 세그먼트, VIP, NAT 매핑표의 원천 데이터: 네트워크팀 협조 필요

부록의 수집 스크립트는 구조를 보여주는 예시입니다. 실제 서버에서 아직 실행해 보지 않았으므로 Phase 1에서 검증해야 합니다.
